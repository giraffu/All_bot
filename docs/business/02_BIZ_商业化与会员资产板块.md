# 02_BIZ_商业化与会员资产板块

## 1. 业务定位

本板块负责 AllBot 的收入转化、会员权益、灵石账本与邀请返佣闭环。当前生产实现已经形成三层结构：

- 支付层：RMB、TON、Telegram Stars 三通道发货
- 资产层：`credits` 单轨灵石账本 + `user_logs` 审计流水
- 裂变层：标准邀请奖励 + 首单返佣 `affiliate_transactions` + 返佣兑换灵石 `affiliate_redeems`

## 2. 已落地能力

### 2.1 多支付通道

- RMB：预建本地订单，支付网关异步回调发货。
- TON：轮询链上转账，按 `tx_hash` 幂等落单并履约。
- Stars：Telegram 官方支付回调发货。

### 2.2 单轨资产

- 所有任务消费、充值到账、返佣兑换都统一落到 `users.credits`。
- 任何灵石变动都要求写 `user_logs`，不能出现“余额变了但没有流水”的旁路。
- Web 个人中心已提供只读灵石账本查询，入口为 `GET /api/users/me/credits/ledger`；普通用户只能查看自己的非 0 收支流水，前端仅展示后端白名单过滤后的上下文。

### 2.3 会员权益

- 套餐既支持“纯灵石包”，也支持“身份 + 灵石”月卡。
- 现有身份体系仍是：`内门弟子`、`核心弟子`、`真传弟子`。
- 月卡续费、升级、低级卡折算高级身份时长都已在履约链路中处理。

### 2.4 邀请返佣闭环

- 标准邀请奖励直接进入灵石账本：
  - 仅邀请注册但未进群：邀请人不获得灵石，被邀请新用户仍保留 `welcome_bonus = +6`
  - 已进群但未生成：邀请人累计获得 5 灵石
  - 首次成功生成内容：邀请人累计获得 10 灵石
  - 老规则已发的 `referral_reward_initial` 会计入累计目标，避免重复补发
- 返佣以 `commission_usdt` 为基准，当前按订单成功履约后入账。
- 邀请人可兑换余额来自 `affiliate_transactions` 汇总，不依赖单独余额字段。
- 已落地“返佣余额兑换灵石”：
  - `1 USDT = 90 credits`
  - `amount_usdt` 接收 4 位小数
  - `credits_granted` 采用 `ROUND_HALF_UP`
  - 记 `CREDITS_REDEEM / OUT / SUCCESS`
- Dashboard 返佣榜与用户中心的口径不同：
  - Dashboard 展示历史累计返佣榜
  - 用户中心关注当前可兑换余额与历史累计/已兑换拆分
  - 用户中心的受邀充值统计只展示产生首单返佣的充值订单，后续 `commission_usdt = 0` 的复购不再累计到该展示口径

## 3. 当前业务边界

- 已上线
  - 充值购买套餐
  - 身份折算
  - 首单返佣入账
  - 返佣兑换灵石
- 未上线
  - 返佣兑换会员身份
  - 返佣提现冻结、审核、打款

因此，知识库中涉及 affiliate 二期时，只能把“兑换身份 / 提现”写成规划，不得写成已实现事实。

## 4. 关键业务规则

- 首单返佣若缺支付汇率或汇率非法，必须失败并回滚，不能把返佣固化成 0。
- 所有支付/返佣链路都需要唯一幂等锚点：本地订单号、外部流水号、`idempotency_key`。
- 返佣兑换重放必须返回首次成功快照，而不是重新读取当前余额后再组装结果。
- 缓存失效要在最终提交成功后触发，否则并发下可能把旧余额写回 Redis。

## 5. 文档维护口径

- “商业化”不再只是充值月卡，应明确覆盖返佣账本与返佣兑换。
- 后续若上线 affiliate 会员兑换或提现，需单独补充新的数据模型与幂等策略，而不是复用现有文案笼统描述。
