# Web 老任务恢复导致无效状态轮询问题分析与可执行评审版

## 1. 文档目的

本文基于当前仓库实际代码、生产日志、数据库记录与运行态语义，对 Web 端“老任务恢复后持续打无效状态轮询”问题做一次与现状一致的评审归纳。

本文重点回答两个问题：

1. 当前线上 `404` 轮询噪音是否确实存在，以及责任边界在哪里。
2. 旧版分析中哪些判断已经过时，修复方案应该如何调整，才能与当前代码实现保持一致。

本文不是最初问题记录，而是用于替换旧分析口径、并可直接作为修复评审输入的“可执行评审版”。

---

## 2. 当前状态摘要

基于当前代码，Web 任务恢复链路已经不是最初那种“所有缺结果的成功任务都会重新恢复 SSE”的状态，而是已经分流成两条路径：

1. 本地残留的 `pending` / `running` 任务，页面刷新后仍会恢复 SSE。
2. 本地处于 `awaitingResult`，或 `status === 'success' && !resultUrl` 的任务，刷新后会改走 `/tasks/{task_id}/result` 轮询，而不是重新恢复 SSE。

与此同时，`/api/tasks/{task_id}/stream` 这条链路在面对 `backend_api /status/{task_id}` 返回 `404` 时，仍然没有把它当作明确终止条件，导致老任务只要被误恢复进 SSE，就会稳定制造无效轮询。

因此，当前真正仍在发生的问题应被表述为：

1. 前端本地 `active_tasks` 中残留的陈旧 `pending/running` 任务，会在刷新后继续恢复 SSE。
2. Web API 的 SSE 实现没有把运行态 `404` 转成明确终止语义，导致持续查询 `backend_api /status/{task_id}`。

---

## 3. 现象描述

线上异常现象可以稳定复现为：

1. `web-api -> backend_api /status/{task_id}` 在短时间内出现大量 `404 Not Found`。
2. 这些 `404` 高度集中在少量固定老任务 ID 上，而不是随机分布。
3. 这些任务在数据库 `history` 中已经存在记录，且 `output_file` 非空，说明结果已持久化。
4. 同时它们不再存在于运行态 Redis 中，因此 `backend_api` 继续返回 `404` 是符合接口语义的。

问题本质不是任务执行失败，而是“前端仍把历史上遗留的运行态任务当作活跃任务恢复进入 SSE，随后 SSE 又缺少 404 终止语义”。

---

## 4. 现网证据

### 4.1 日志证据

在不同时间窗的多次生产日志核查中，观察到同一类稳定模式：

1. `web-api` 日志中会出现少量固定老任务 ID 持续请求 `http://127.0.0.1:8003/status/{task_id}` 并收到 `404 Not Found`。
2. `backend_api` 日志中也能看到同样的 `/status/{task_id}` 请求持续返回 `404`。
3. 这些 `404` 不是随机散点，而是高度集中在极少数历史任务上，符合“陈旧任务反复被恢复并轮询”的特征。
4. 不同采样窗口内，任务 ID 和次数可能不同，但模式一致：同一 `task_id` 被重复查询，且其他正在运行的任务 `status/*` 仍正常返回 `200`。

这说明异常不是前端单侧展示问题，而是已经实实在在落到了服务端请求层面。

### 4.2 数据库证据

对上述任务进行数据库交叉验证后确认：

1. 3 个 `task_id` 均已存在于 `history` 表。
2. 3 个任务均已存在 `output_file`。
3. 记录创建时间分别落在 `2026-05-12` 与 `2026-05-15`，属于明确的历史任务，而非刚提交的新任务。

因此可以确认：

1. 这些任务不是“尚未完成的运行任务”。
2. 它们已经脱离运行态，只剩历史结果语义。

### 4.3 运行态语义证据

当前中控 `backend_api /status/{task_id}` 的语义是：

1. 只读取 Redis 中当前运行态任务。
2. Redis 中不存在对应任务时，直接返回 `404 Task not found`。

这意味着：

1. 对历史任务返回 `404` 是正确行为。
2. 真正异常的是 Web 层仍在持续把这些历史任务路由到运行态接口。

## 5. 当前代码链路分析

### 5.1 前端恢复逻辑的现状

当前前端恢复逻辑并不是旧分析中描述的“`success && !resultUrl` 也会恢复 SSE”。

现状是：

1. `restoreTasksFromStorage()` 会从本地恢复 `active_tasks`。
2. 每个任务会先经过 `restorePersistedTask()` 做恢复分流。
3. 如果任务满足以下任一条件：
   - `task.awaitingResult === true`
   - `task.status === 'success' && !task.resultUrl`
   则会被标记为 `poll_result`，随后走 `/tasks/{task_id}/result` 轮询。
4. 只有恢复结果为 `resume_sse` 的任务，才会继续调用 `startListening()` 建立 SSE。
5. 虽然 `shouldResumeTaskListening()` 本身仍把 `success && !resultUrl` 视为“可恢复监听”的状态，但在当前调用顺序里，`restorePersistedTask()` 会先把这类任务拦截并改走 `poll_result`，因此线上实际行为并不会先落回 SSE。

换句话说，当前代码已经做了一个重要修正：

1. “等待结果 URL 的完成态任务”不再回到 SSE。
2. 真正还会恢复 SSE 的，是本地状态仍然停留在 `pending` / `running` 的任务。

因此，旧版文档把“`success && !resultUrl` 被恢复成 SSE”列为当前主根因，这一判断已经与现代码不一致，应删除或改写。

### 5.2 前端为什么仍会残留老任务

虽然上述完成态分流已经存在，但前端仍存在一个现实问题：

1. `active_tasks` 会持续写入本地存储。
2. 当前没有针对本地任务的持久化 TTL 或统一陈旧清理机制。
3. 如果用户没有主动关闭任务悬浮球，旧任务可能长时间滞留在本地。

这会产生一个后果：

1. 某些本应早已结束的任务，如果本地状态仍停留在 `pending` 或 `running`，刷新页面后仍会被恢复进入 SSE。
2. 这类任务才是当前 `404` 轮询噪音的主要来源。

### 5.3 Web API 的 SSE 当前行为

`/api/tasks/{task_id}/stream` 目前的行为如下：

1. 建立 Redis Pub/Sub 订阅。
2. 启动时主动请求一次 `backend_api /status/{task_id}`。
3. 如果拿到 `running`、`done`、`error`、`cancelled` 等状态，则按预期继续处理或结束。
4. 如果 `backend_api` 返回 `404`，`get_task_status_full()` 不会返回明确的 `not_found` 信号，而是统一折叠成 `None`。
5. 在 `is_running == False` 阶段，SSE 每 5 秒会再次请求一次 `backend_api /status/{task_id}`。

这意味着当前实现中：

1. `404` 没有被视为“终止条件”。
2. 它被当成“暂时没拿到状态，稍后再查”。

于是只要一个老任务误进入 SSE，就会形成稳定的 `404` 周期轮询。

### 5.4 backend_api 的状态接口语义

当前 `backend_api /status/{task_id}` 的实现是明确且合理的：

1. `enqueue_task()` 入队时会立即写 Redis 任务元数据。
2. `get_task_status()` 只查询 Redis 运行态任务。
3. 不存在对应任务时直接返回 `404`。

接口职责非常清晰：

1. 查询当前运行态任务状态。
2. 不负责查询历史结果。

因此，本问题不应通过修改 `backend_api /status/{task_id}` 去“兼容历史任务”来解决。

## 6. 根因修正版归纳

结合当前代码与日志，根因应修正为以下两层。

### 6.1 第一层根因：本地残留的陈旧 `pending/running` 任务被恢复进 SSE

当前真正有问题的不是“缺 `resultUrl` 的成功任务”，而是：

1. 某些老任务长期残留在本地 `active_tasks`。
2. 它们的本地状态仍是 `pending` 或 `running`。
3. 页面刷新后，这些任务会重新恢复 SSE 监听。

这类任务实际上可能早已：

1. 完成并落库；
2. 或已经不在 Redis 运行态；
3. 但前端本地状态没有同步清理。

因此，当前前端层面的核心问题不是“结果恢复链路缺失”，而是“陈旧运行态任务缺乏本地生命周期治理”。

### 6.2 第二层根因：SSE 对运行态 `404` 缺少明确终止语义

即便前端误恢复了老任务，理论上服务端也应该尽快止损。

但当前 `/api/tasks/{task_id}/stream`：

1. 把 `404` 吞成 `None`；
2. 不区分“短暂无状态”和“明确不存在于运行态”；
3. 导致在非运行态阶段持续每 5 秒轮询。

于是形成完整放大链路：

1. 陈旧任务恢复进入 SSE；
2. SSE 初始状态查询命中 `404`；
3. `404` 没有被当作终止条件；
4. `web-api` 持续请求 `backend_api /status/{task_id}`；
5. 日志被稳定刷屏。

---

## 7. 为什么这不是 backend_api 的 bug

这个问题容易被误判为“backend_api 状态丢失”，但当前证据并不支持这种结论。

原因如下：

1. 目标任务已经在 `history` 中落库，结果没有丢。
2. `output_file` 已存在，说明主执行链路已完成持久化。
3. `backend_api /status/{task_id}` 的职责本来就只是查询当前运行态。
4. 对已脱离运行态的历史任务返回 `404`，恰好是在正确表达当前接口语义。

因此真正需要修正的是：

1. 前端对陈旧本地任务的恢复与清理策略；
2. Web API `stream` 对运行态 `404` 的处理方式。

不应该通过“让 `/status/{task_id}` 顺带查历史库”来模糊职责边界。

---

## 8. 旧版分析中需要删除或修正的结论

为避免后续评审继续基于过时结论展开，以下口径应明确删除或改写。

### 8.1 应删除的旧判断

以下结论已不符合当前代码现状：

1. “`status === 'success' && !resultUrl` 的任务刷新后会恢复 SSE。”
2. “当前前端主问题是已完成但未拿到 `resultUrl` 的任务被错误恢复到状态监听链路。”
3. “优先修 `shouldResumeTaskListening()`，就能直接切断这批 404 噪音。”

这些判断在曾经的旧实现阶段可能成立，但对当前代码已不成立。

### 8.2 应保留的判断

以下结论仍然成立：

1. 运行态 `404` 轮询噪音是真实存在的。
2. `backend_api /status/{task_id}` 返回 `404` 是符合语义的。
3. `/api/tasks/{task_id}/stream` 需要补充显式终止逻辑。
4. 历史结果不应重新回到运行态接口。

### 8.3 应新增的判断

当前评审必须新增下面这层认识：

1. `awaitingResult` 与 `success && !resultUrl` 已经是结果恢复链路，不是当前 404 SSE 噪音的主因。
2. 当前主因是陈旧的 `pending/running` 本地任务残留。
3. 前端如果要做收口，重点应放在“本地任务生命周期治理”，而不是重复改一遍已存在的结果恢复分流。

## 9. 修正后的解决方案设计

### 9.1 方案目标

修复目标不是简单减少日志，而是恢复清晰的职责边界：

1. 真正仍在运行的任务，走 `stream + /status/{task_id}`。
2. 已进入结果恢复阶段的任务，走 `/tasks/{task_id}/result`。
3. 历史任务不再长时间滞留在本地运行态集合中。
4. 对于误进入 SSE 的非运行态任务，服务端要尽快止损。

### 9.2 Web API 方案：第一优先级止血项

当前最值得优先落地的是后端兜底，因为它能直接切断持续 404 轮询。

执行要点如下：

1. `get_task_status_full()` 不要再把 `404` 简单吞成 `None`，而是返回明确的 `not_found` 信号。
2. `event_generator()` 在初始化阶段或轮询阶段遇到 `not_found` 时，不应继续无限轮询。
3. 遇到 `not_found` 后，应在 Web API 内部补一次当前用户维度的历史判定：
   - 若该任务在当前用户维度上已存在历史记录，则向前端发送一次当前协议已兼容的 `status=success` 事件，再关闭 SSE；
   - 若该任务既无运行态，也不存在当前用户可访问的历史记录，则向前端发送一次当前协议已兼容的 `status=failed` 事件，再关闭 SSE。

这里要特别注意：

1. 不建议“只关闭 SSE 连接而不发送任何终态事件”。
2. 因为当前前端在连接异常时会走 `source.onerror` 并对 `pending/running` 任务进行有限重连。
3. 如果后端只静默断开，仍会留下额外重连噪音。
4. 当前前端只显式处理 `status=success` 与 `status=failed` 两类终态，不兼容新的 `terminated`、`not_found`、`cancelled` 等新增状态名。
5. 因此在本轮止血方案里，不应引入新的 SSE 终态枚举，除非同步修改前端消费逻辑。

因此，评审版建议采用下面这组兼容性更稳的执行顺序：

1. 先发送明确终态；
2. 再主动结束 SSE。
3. 其中“明确终态”必须是当前前端已能消费的终态，而不是仅对后端语义友好的新状态名。

落地时还应同时满足以下约束：

1. 这里的“历史判定”应以 `current_user.id + task_id` 为边界，不能只按 `task_id` 做全局历史存在判断。
2. 若历史记录已存在但结果 URL 尚未就绪，也仍可先发送 `status=success`，让前端进入既有的结果恢复链路，再由 `/tasks/{task_id}/result` 返回 `pending_result` 或最终结果。
3. `404` 只是“明确不在运行态”的信号，不应与网络超时、连接失败、`5xx` 混为一类；后者仍应视作暂时性异常，不宜直接终止 SSE。

### 9.3 前端方案：聚焦陈旧本地任务治理

前端仍然需要补治理，但修复重点应调整。

执行要点如下：

1. 保留当前已存在的“`awaitingResult` / `success && !resultUrl` 走结果轮询”的恢复分流。
2. 不要再把这部分作为主修复目标重复改造。
3. 为 `active_tasks` 增加持久化时间信息或最近活跃时间信息。
4. 页面初始化恢复时，对明显陈旧的 `pending/running` 任务做清理或降级。

需要注意的是：

1. 当前 `/tasks/{task_id}/result` 只能表达“结果已就绪”或“结果尚未就绪”，不能可靠区分“仍在运行”和“已经成为历史僵尸任务”。
2. 因此不建议在前端仅靠调用一次 `/tasks/{task_id}/result` 去决定某个 `pending/running` 任务是否还应该恢复 SSE。
3. 也不建议设置过短的任务年龄阈值，否则可能误伤真实长任务。

如果要做年龄阈值：

1. 应基于后端运行态任务的实际 TTL 和生命周期来设计；
2. 只能作为“清理明显陈旧任务”的兜底，不应作为运行态判断主依据。

### 9.4 不建议的方案

不建议通过以下方式“修问题”：

1. 不建议把 `backend_api /status/{task_id}` 改成同时查历史库。
2. 不建议继续把 `404` 视为普通空状态并无限重试。
3. 不建议只依赖前端 `source.onerror` 的重连上限止损。
4. 不建议把“`success && !resultUrl` 走结果恢复”再次当成主改造项。
5. 不建议给所有 `pending/running` 任务直接套一个激进的短时间年龄阈值。

## 10. 推荐落地顺序

### 10.1 第一优先级：Web API 先止血

先改 `/api/tasks/{task_id}/stream`：

1. 识别 `404` 为明确 `not_found`。
2. 对 `not_found` 触发一次“当前用户维度”的历史判定。
3. 若历史存在，则发送当前前端已兼容的 `status=success` 事件，让前端切换到 `/tasks/{task_id}/result`。
4. 若历史不存在，则发送当前前端已兼容的 `status=failed` 事件。
5. 在发送完兼容终态后结束 SSE，停止后台空转。

这样可以最快把线上稳定刷屏的 `404` 请求压下来，也便于先做一轮小范围联调验证。

### 10.2 第二优先级：前端补本地任务生命周期治理

再补前端本地任务治理：

1. 给 `active_tasks` 增加时间维度。
2. 清理明显陈旧的 `pending/running` 残留任务。
3. 保持当前 `awaitingResult` 与 `success && !resultUrl` 的结果恢复分流不变。

### 10.3 第三优先级：如有需要，再扩展更清晰的终止协议

如果后续想把前后端协议进一步收敛得更清晰，可以考虑：

1. 为 SSE 增加更明确的“任务已不在运行态”事件类型；
2. 让前端对这类事件直接收敛到历史查看或结果恢复逻辑；
3. 但这属于协议优化，不是当前止血的必要前置条件；
4. 在这一步之前，不要提前在后端单独引入新的 SSE 终态状态名。

## 11. 回归测试建议

### 11.1 页面刷新恢复场景

1. 新任务提交后刷新页面，仍处于运行态，应正确恢复 SSE。
2. 任务进入 `awaitingResult` 后刷新页面，应继续走 `/tasks/{task_id}/result` 轮询，而不是恢复 SSE。
3. `status === 'success' && !resultUrl` 的任务刷新页面后，应直接走结果恢复链路。
4. 本地残留的历史 `pending/running` 任务刷新后，不应长期维持对 `/status/{task_id}` 的 404 轮询。

### 11.2 SSE 404 终止场景

1. `/status/{task_id}` 首次返回 `404` 且当前用户历史存在记录时，SSE 应发送当前前端已兼容的 `status=success` 事件并结束。
2. 该 `success` 事件发出后，前端应进入既有结果恢复链路，而不是重新恢复 SSE。
3. `/status/{task_id}` 返回 `404` 且当前用户历史不存在记录时，SSE 应发送当前前端已兼容的 `status=failed` 事件并结束。
4. SSE 正常结束后，前端不应因 `source.onerror` 再触发长时间的重复重连噪音。
5. 当 `backend_api` 只是超时、连接失败或 `5xx` 时，不应误走 `not_found` 终止分支。
6. `status=success` 后转入 `/tasks/{task_id}/result` 的既有结果恢复链路，应在联调中显式验证一次，确保不会被误判为重新恢复 SSE。

### 11.3 日志验证

1. 同类历史任务刷新页面后，不应再看到相同 `task_id` 持续刷 `/status/{task_id}` `404`。
2. `web-api` 中相关 `404` 日志量应明显下降。
3. `backend_api` 中对同一历史任务的重复 `404` 应接近归零。

---

## 12. 结论

结合当前代码与线上证据，本问题应被重新表述为：

1. 前端已经把 `awaitingResult` 与 `success && !resultUrl` 分流到了结果恢复链路。
2. 当前真正仍会误恢复进 SSE 的，是本地残留的陈旧 `pending/running` 任务。
3. Web API 的 SSE 对运行态 `404` 没有明确终止语义，导致这些陈旧任务一旦进入 SSE，就会稳定制造无效轮询。

因此，最合理的修复方向不是重复修改已存在的结果恢复分流，而是：

1. 优先在 Web API `stream` 中把运行态 `404` 升级为明确终止信号，但终止事件必须保持对当前前端协议兼容；
2. 对“当前用户历史存在”的任务，发送 `status=success` 后关闭 SSE，让前端走既有 `/tasks/{task_id}/result` 恢复链路；
3. 对“既无运行态也无当前用户历史”的任务，发送 `status=failed` 后关闭 SSE；
4. 再在前端补充本地 `active_tasks` 的生命周期治理，重点清理陈旧 `pending/running` 残留任务。

这份文档以下面这条原则作为最终落地约束：

1. 本轮止血只修“404 语义”和“陈旧本地任务治理”；
2. 不改 `backend_api /status/{task_id}` 的职责边界；
3. 不在未同步修改前端前提下引入新的 SSE 状态枚举；
4. 不重复改造已经存在的结果恢复分流。

这样既能消除当前日志噪音，又能保持“运行态接口”和“历史结果接口”的职责边界清晰。
